-- VERIFIED FACTS --
 . OAuth2 authorize URL is GET https://account.withings.com/oauth2_user/authorize2 with required params response_type=code, client_id, state, scope (comma-separated), redirect_uri; optional mode=demo for a demo user. (https://developer.withings.com/openapi.yaml, oauth2-authorize operation; https://developer.withings.com/developer-guide/v3/integration-guide/public-health-data-api/get-access/oauth-authorization-url/)
 . state is required and described as a CSRF protection value that is echoed back on the redirect and 'should be validated at this point'. (https://developer.withings.com/openapi.yaml; oauth-authorization-url guide page)
 . The authorization code is only valid for 30 seconds — exchange immediately. (oauth-authorization-url guide page; https://developer.withings.com/llms.md)
 . Token endpoint is POST https://wbsapi.withings.net/v2/oauth2 (Content-Type: application/x-www-form-urlencoded) with a Withings-specific action=requesttoken parameter plus standard OAuth params. For the public API ('Using client secret' schema TokenRequestWithClientSecret) required params are: action=requesttoken, client_id, client_secret, grant_type=authorization_code, code, redirect_uri. Refresh: action=requesttoken, client_id, client_secret, grant_type=refresh_token, refresh_token. An alternative 'Using signature' schema (client_id + nonce + HMAC signature instead of client_secret) exists for contracted partners. (https://developer.withings.com/openapi.yaml, oauth2-getaccesstoken operation)
 . Responses are wrapped in an envelope {"status": <int>, "body": {...}}; status 0 = success (HTTP status is 200 even on API errors). Token response body contains userid, access_token, refresh_token, scope, expires_in, token_type=Bearer (guide also lists csrf_token). Withings says to persist the userid. (https://developer.withings.com/openapi.yaml; https://developer.withings.com/llms.md)
 . Token lifetimes: access_token expires after 3 hours (expires_in=10800); refresh_token expires after 1 year. Refresh tokens ROTATE: every requesttoken call returns a new refresh_token, and the previous refresh_token becomes invalid 8 hours after the new one is issued, or as soon as the new access_token is used — always persist the new refresh_token. (https://developer.withings.com/developer-guide/v3/integration-guide/dropship-cellular/get-access/access-and-refresh-tokens/; https://developer.withings.com/llms.md)
 . Public API scopes are exactly: user.info, user.metrics, user.activity, user.sleepevents; blood-pressure measurements and appli=4 notifications fall under user.metrics. (oauth-authorization-url guide page; https://developer.withings.com/developer-guide/v3/data-api/notifications/notification-content; https://developer.withings.com/llms.md)
 . Measure endpoint: POST https://wbsapi.withings.net/measure with action=getmeas, Authorization: Bearer <access_token>. Params: meastype (single int) or meastypes (comma-separated list), category (1 = real measures, 2 = user objectives), startdate/enddate (unix timestamps), lastupdate (unix timestamp, 'requesting data that were updated or created after this date... Use this instead of startdate + enddate'), offset. (https://developer.withings.com/openapi.yaml, measure-getmeas operation)
 . Measurement type IDs for BP confirmed current: 9 = Diastolic Blood Pressure (mmHg), 10 = Systolic Blood Pressure (mmHg), 11 = Heart Pulse (bpm, 'only for BPM and scale devices'). Also relevant for BP devices: 54 = SpO2 (%), 130 = Atrial fibrillation result (classification integer 0-13, not a physical measurement). (https://developer.withings.com/openapi.yaml, measure-getmeas meastype table and measure_object schema)
 . Value encoding: each measure has value, type, unit; real value = value * 10^unit (unit is a power-of-ten exponent, e.g. value=20, unit=-1 -> 2). The algo field is deprecated. (https://developer.withings.com/openapi.yaml, measure_object schema)
 . measuregrp fields: grpid (int64 unique group id), date (measurement time), created (stored time), modified (last-updated time), category (as in the category input param), deviceid/hash_deviceid, model/modelid, measures[]. A measure group bundles measures taken at the same time — a BP reading is one group with systole, diastole and heartrate measures — and 'Every time a measure is create/updated/deleted, the corresponding measure group is updated.' (https://developer.withings.com/openapi.yaml, measuregrp_object schema and getmeas response description)
 . attrib values: 0 = captured by a device and unambiguously belongs to this user; 1 = captured by a device but ambiguous (may belong to other users); 2 = entered manually for this user; 4 = entered manually during user creation (may be inaccurate); 5 = 'Measure auto, it's only for the Blood Pressure Monitor. This device can make many measures and computed the best value'; 7 = measure confirmed by user; 8 = same as attrib 0; 15 = performed in guided conditions (Nerve Health Score). (https://developer.withings.com/openapi.yaml, measuregrp_object.attrib)
 . Pagination/cursor: response body contains updatetime (server time), timezone, measuregrps, more, offset. When more=1, re-call with the returned offset until more=0. For sync, official guidance: pass lastupdate = timestamp of your last successful fetch and 'the Data API returns everything created or modified since, including any updates you missed if a notification was lost'; store the response's updatetime as your next lastupdate. startdate/enddate is for targeting a precise window (e.g. the one from a webhook payload). (https://developer.withings.com/openapi.yaml; /developer-guide/v3/integration-guide/public-health-data-api/data-api/fetch-data-example; https://developer.withings.com/llms.md)
 . Notify API: POST https://wbsapi.withings.net/notify with Authorization: Bearer token. Actions: subscribe (params: action=subscribe, callbackurl (max 255 chars), appli (required int), optional comment), get, list (defaults to appli=1 if unspecified), revoke, update (callbackurl+appli identify the subscription; new_callbackurl / new_appli / comment change it). Subscriptions are per user (per access token) and per appli. (https://developer.withings.com/openapi.yaml, notify-* operations)
 . appli categories (authoritative table): 1 = Weight & body composition (user.metrics), 2 = Temperature (user.metrics), 4 = Blood pressure & heart rate (user.metrics) — 'Triggered when a new blood pressure measurement (and heart rate, when supported) was recorded', covering meastypes 9, 10, 11, 54 — 16 = Activity (user.activity), 44 = Sleep summary (user.activity), 46 = User profile change (user.info; payload has action=delete|unlink|update), 50/51/52 = sleep events (user.sleepevents), 53 = unassociated device, 54 = ECG, 55 = ECG failed, 58 = Glucose, 60 = Survey, 61 = Stethoscope, 62 = HRV, 98-100 = Live-sync bed events. So YES: appli=4 is the one to subscribe for BP. (https://developer.withings.com/developer-guide/v3/data-api/notifications/notification-content)
 . Notification delivery: Withings sends an application/x-www-form-urlencoded POST to the callback URL; standard fields are userid (int), appli (int), startdate and enddate (unix epoch); example for BP: 'userid=12345&appli=4&startdate=1530576000&enddate=1530576120'. Recommended next step for appli=4 is to call Measure - Getmeas for that window (or with lastupdate). Endpoint must return HTTP 2xx within a few seconds. (https://developer.withings.com/developer-guide/v3/data-api/notifications/notification-content; notification-overview)
 . Callback validation at subscribe time: 'Withings sends a HEAD request to verify your URL is reachable before registering it. Make sure your server handles HEAD and returns a 2xx status code.' Callback URL rules: HTTPS only; no IP addresses or localhost (must be a proper domain); ports 80/443 only; max 255 characters. Apps whose URL violates these run in 'restricted mode' limited to 10 linked users (dev/testing only). (https://developer.withings.com/developer-guide/v3/data-api/notifications/notification-subscribe/)
 . Notification retry behavior: on failure, 5 retry cycles over ~5 hours at T+0, +10s, +1min, +1hr, +4hr, each cycle making 2 HTTP attempts (10 total). 4 failed notifications in a row triggers a warning email (max 4 emails); 20 days of unresolved failures auto-cancels the subscription with a final notice email. Missed notifications are NOT redelivered — backfill with getmeas lastupdate. Typical delivery delay is under 2 minutes with no real-time SLA on the standard plan. (https://developer.withings.com/developer-guide/v3/data-api/notifications/notification-overview/)
 . Developer account: the Public API requires no contract — create an app in the Developer Dashboard at https://developer.withings.com/dashboard/ (a Withings account is needed; Withings recommends a dedicated org account), which yields client_id and client_secret; apps can be updated/deleted there, and redirect_uri must be pre-registered as the app's 'Callback Url' (multiple URLs allowed, comma-separated; a redirect URL with path and query args is valid). The Public API runs on the EU Medical Cloud endpoint https://wbsapi.withings.net (GDPR, ISO 27001:2017, HDS certified) with free access. (https://developer.withings.com/openapi.yaml oauth2-authorize redirect_uri description; /developer-guide/v3/integration-guide/public-health-data-api/developer-account/create-your-accesses-no-medical-cloud)
 . Demo/sandbox: two mechanisms — (a) append mode=demo to the authorize URL to run the OAuth flow against a demo user with dummy data, no real device required; (b) 'OAuth 2.0 - Get Demo Access' service (action=getdemoaccess on https://wbsapi.withings.net/v2/oauth2 with client_id, signature, nonce, scope_oauth2) which 'gives your clientID access to a demo account containing dummy data'. (oauth-authorization-url guide page; https://developer.withings.com/openapi.yaml oauth2-getdemoaccess operation)
 . Relevant error statuses (in the JSON envelope): 0 success, 100 no data, 247 invalid userid, 286 no such subscription, 293 callback URL absent/incorrect, 305 missing parameter, 342 OAuth credentials absent/incorrect, 343 access token absent/invalid, 601 too many requests. Best-practice guidance: don't poll more than once every 10 minutes per user; prefer webhook + pull-on-notify. (https://developer.withings.com/llms.md, consistent with openapi.yaml status descriptions)
-- UNCERTAINTIES --
 ? Official-doc conflict: developer.withings.com/llms.md ('Complete Reference for AI Agents') lists appli 1=Body, 4=Sleep, 16=Blood pressure, 44=ECG, 46=Activity — this CONTRADICTS the detailed notification-content guide and the long-standing API reference, which say appli 4 = Blood pressure & heart rate, 16 = Activity, 44 = Sleep. The detailed guide is internally consistent (per-appli payload examples, scope mapping) and should be trusted; treat llms.md's appli table as erroneous, but a smoke test (subscribe appli=4, take a BP reading on the demo account) is advisable before hard-coding.
 ? llms.md also lists meastype 140 = Vascular Age while openapi.yaml lists 155 = Vascular age (and no 140). Irrelevant to BP (9/10/11 agree everywhere) but another sign llms.md drifts from the spec.
 ? How deleted or corrected measurements appear in getmeas output is not explicitly documented. The spec only says the measure group is 'updated' whenever a measure is created/updated/deleted and that lastupdate returns groups created or updated since the timestamp; whether a fully deleted group is returned at all (e.g. with an empty measures array or a flag) is unspecified. Upserting by grpid handles corrections; deletion detection needs empirical testing.
 ? No documented deduplication token/signature on notification deliveries (no delivery id, no HMAC on the webhook payload, no documented Withings source-IP list). Since each retry cycle makes 2 HTTP attempts, duplicate deliveries are possible — dedupe on (userid, appli, startdate, enddate) and rely on idempotent grpid upserts. Webhook payloads are unauthenticated per the docs; validate by fetching data with the stored token rather than trusting the payload.
 ? Exact timeout for the subscribe-time HEAD check and for notification POST responses is not specified ('return 2xx within a few seconds'; 'No timeout duration is specified').
 ? The refresh-token lifetime (1 year) and 8-hour old-token grace period were read from the dropship-cellular 'Access and refresh tokens' guide page because the public-health-data-api variant of that page currently redirects to the homepage; token semantics are shared across solutions (the spec documents one common oauth2-getaccesstoken operation), but the 1-year figure was not re-verified on a Public-API-specific page. The support.withings.com article on refresh-token expiration returned HTTP 403.
 ? The token response 'csrf_token' field appears in the dropship guide's response list but not in llms.md's example; presence for public-API responses unverified.
 ? Rate limits: llms.md advises polling no more than every 10 minutes per user, and status 601 = Too Many Requests exists, but exact numeric request-per-minute quotas for the Public API were not found in the fetched docs.
 ? Whether the notify subscribe HEAD validation also recurs periodically (re-validation of existing subscriptions) is not documented.
-- IMPLEMENTATION NOTES --
Server-side BP connector plan (all endpoints verified 2026-08-29):

1) Registration: create an app at https://developer.withings.com/dashboard/ (no contract needed for the Public API). Register the exact HTTPS redirect_uri as the app's Callback Url. Store client_id/client_secret.

2) OAuth: redirect to https://account.withings.com/oauth2_user/authorize2?response_type=code&client_id=...&scope=user.metrics&redirect_uri=...&state=<random> (add user.info if you want device/account info; add mode=demo for sandbox testing). Validate state on callback, then within 30 seconds POST form-encoded to https://wbsapi.withings.net/v2/oauth2 with action=requesttoken&grant_type=authorization_code&client_id&client_secret&code&redirect_uri. Note the non-standard envelope: HTTP 200 with {status, body} — check status==0, tokens are in body. Persist body.userid. Refresh with grant_type=refresh_token; refresh tokens rotate on EVERY call (old one dies 8h after rotation or when the new access token is used), so persist the new refresh_token atomically before using the new access_token; access token lives 3h (expires_in=10800). Handle status 343 by refreshing; treat a failed refresh as needing re-authorization (there is no code-recovery service for non-contracted apps).

3) Pull: POST https://wbsapi.withings.net/measure (Bearer auth, form-encoded) action=getmeas&meastypes=9,10,11&category=1. For sync use lastupdate=<previous response's updatetime> (NOT startdate/enddate), loop while more==1 passing back offset. Each BP reading is one measuregrp: grpid is the stable idempotency key; decode each measure as value*10^unit; systolic=type 10, diastolic=type 9, pulse=type 11 (optionally 54 SpO2, 130 AFib for BPM Core/BeamO). Keep attrib: 0/8 device-attributed, 1 ambiguous, 2/4 manual, 5 = BPM auto-mode best-of-N value. Upsert by grpid using the group's modified timestamp to absorb corrections; deletion representation is undocumented — test empirically.

4) Webhooks: per user, POST https://wbsapi.withings.net/notify with action=subscribe&callbackurl=...&appli=4 (blood pressure & heart rate; a separate namespace from meastype). Callback must be HTTPS, real domain (no IP/localhost), port 443/80, <=255 chars, and MUST answer HEAD with 2xx or the subscribe fails (non-compliant URLs cap the app at 10 users). Handler: accept both HEAD and POST, return 2xx fast (enqueue, don't process inline). Payload is application/x-www-form-urlencoded: userid, appli, startdate, enddate. Don't trust payload contents — respond 2xx, then fetch via getmeas with lastupdate for that user. Retries: 10 attempts over ~5h; missed events are never redelivered (lastupdate backfill covers gaps); 20 days of failures auto-cancels the subscription, so also run a daily reconciliation poll and periodically verify subscriptions with action=list.

5) Sandbox: use mode=demo on the authorize URL for an end-to-end test with dummy data before pairing the real BPM.

Caution: do not code-gen from https://developer.withings.com/llms.md alone — its appli table is wrong (says 16=BP); the notification-content guide and openapi.yaml are the authorities.

-- VERIFIED FACTS --
 . Current API is V2 only; the info section of the OpenAPI spec (https://api.ouraring.com/v2/static/json/openapi-1.37.json) states V2 'is the only available integration point for Oura data. The previous V1 API has been sunset.' The getting-started page (https://cloud.ouraring.com/docs/) dates V1 removal to January 22, 2024.
 . Base URL for data requests is https://api.ouraring.com (confirmed by example call 'GET https://api.ouraring.com/v2/usercollection/personal_info' in the spec info section and by NEXT_PUBLIC_EXTAPI_V2_URL=https://api.ouraring.com embedded in developer.ouraring.com).
 . Personal access tokens 'were deprecated in December 2025 and are no longer available for use' (spec info section, openapi-1.37.json). OAuth2 is the only supported auth for user data.
 . OAuth2 authorization code grant: authorization endpoint https://cloud.ouraring.com/oauth/authorize, token endpoint https://api.ouraring.com/oauth/token (both from https://cloud.ouraring.com/docs/authentication and the spec's securitySchemes). Params: response_type=code, client_id, redirect_uri (optional but recommended), scope (space-separated), state (recommended). Token response: access_token, refresh_token, expires_in, token_type. Refresh tokens are single-use (invalidated after use). Implicit flow (response_type=token) exists but has no refresh tokens; tokens expire at 30 days (cloud.ouraring.com/docs/authentication).
 . OAuth2 scopes per the OpenAPI securitySchemes: email, personal, daily, heartrate, workout, tag, session, spo2Daily (the human-readable auth page lists the last one as 'spo2'). Access tokens go in 'Authorization: Bearer <token>'. personal_info's id field is accessible with any token, no scope required (Personal Info Routes tag description).
 . Data routes verified in openapi-1.37.json (all GET, all under https://api.ouraring.com): /v2/usercollection/daily_sleep, /v2/usercollection/daily_readiness, /v2/usercollection/daily_activity, /v2/usercollection/sleep, /v2/usercollection/heartrate, /v2/usercollection/daily_spo2, /v2/usercollection/daily_stress, /v2/usercollection/daily_resilience, /v2/usercollection/daily_cardiovascular_age, /v2/usercollection/vO2_max (capital O in route), /v2/usercollection/workout, /v2/usercollection/session, /v2/usercollection/tag, /v2/usercollection/enhanced_tag, /v2/usercollection/sleep_time, /v2/usercollection/rest_mode_period, /v2/usercollection/ring_configuration, /v2/usercollection/ring_battery_level, /v2/usercollection/personal_info. Each collection (except personal_info, heartrate, ring_battery_level) also has a /{document_id} single-document GET. Every usercollection route has a /v2/sandbox/usercollection/* twin with fake data for development (no Oura account needed).
 . There is no dedicated HRV endpoint: HRV lives inside the sleep session model (/v2/usercollection/sleep → PublicModifiedSleepModel fields 'average_hrv' and time-series 'hrv') and inside sessions ('heart_rate_variability' in PublicSession). The /v2/usercollection/heartrate route returns only bpm/source/timestamp rows (PublicHeartRateRow) at 5-minute increments, per the Heart Rate Routes description.
 . Temperature deviation lives on daily readiness: PublicDailyReadiness has 'temperature_deviation' and 'temperature_trend_deviation' plus contributors including body_temperature, hrv_balance, resting_heart_rate, sleep_regularity (openapi-1.37.json schemas).
 . SpO2: PublicDailySpO2 has spo2_percentage and breathing_disturbance_index; Daily Spo2 Routes note data only exists for Gen 3 rings. Stress: PublicDailyStress has stress_high, recovery_high, day_summary. Resilience: DailyResilienceModel has level + contributors.
 . The plain 'tag' route is deprecated per the Tag Routes tag description in the spec: 'Tag is deprecated. We recommend transitioning to Enhanced Tag.' EnhancedTagModel fields: tag_type_code, custom_name, comment, start_day/start_time, end_day/end_time.
 . List routes paginate with next_token and accept start_date/end_date (heartrate uses start_datetime/end_datetime plus a 'latest' param); all list routes also accept a 'fields' query param (openapi-1.37.json parameters).
 . Webhook API (openapi-1.37.json): POST /v2/webhook/subscription (create), GET /v2/webhook/subscription (list), GET/PUT/DELETE /v2/webhook/subscription/{id}, PUT /v2/webhook/subscription/renew/{id}. These use x-client-id and x-client-secret headers (NOT the user bearer token). Create body: {callback_url, verification_token, event_type, data_type} — all required. One subscription per (event_type, data_type) pair.
 . Webhook event_type enum (WebhookOperation): create, update, delete. data_type enum (ExtApiV2DataType): tag, enhanced_tag, workout, session, sleep, daily_sleep, daily_readiness, daily_activity, daily_spo2, sleep_time, rest_mode_period, ring_configuration, daily_stress, daily_cardiovascular_age, daily_resilience, vo2_max, meal. Note: no heartrate webhook data type.
 . Webhook verification challenge (spec Webhook Subscription Routes tag): on subscription creation Oura sends GET {callback_url}?verification_token=...&challenge=... ; your endpoint must check the token and respond with JSON {"challenge": "<same string>"}; subscription activates on success.
 . Webhook event payload (POST to callback): JSON body {event_type, data_type, object_id, event_time, user_id} with headers x-oura-signature (HMAC-SHA256, hex uppercase, computed over timestamp + JSON body using the client secret) and x-oura-timestamp. Handlers should respond 2xx within 10 seconds and then fetch the full document by object_id via the API. Responding 410 auto-cancels the subscription; failed deliveries are retried 10 times (~1 hour window). Subscriptions carry an expiration_time (WebhookSubscriptionModel) and are renewed via PUT /v2/webhook/subscription/renew/{id}.
 . Rate limits (spec info section): two layers — per-access-token and per-application aggregate; exceeding either returns 429 with headers Retry-After, X-RateLimit-Limit, X-RateLimit-Window, X-RateLimit-Reset, X-RateLimit-Tier. Oura strongly recommends webhooks: 'We have not had customers hit rate limits with webhooks properly implemented.'
 . Data-availability semantics (spec info + webhook FAQ): data appears only after the ring syncs with the mobile app; webhook notifications arrive ~30 seconds after sync. Sleep/readiness require the user to open the Oura app to sync, while daily activity and daily stress may sync in the background. Recommended pattern: one historical backfill request per user at connect time, then webhooks for ongoing updates. 403 Forbidden also fires when the user's Oura subscription has expired; unapproved API apps are limited to 10 users; users must consent per data type.
 . OpenAPI response schemas: list responses are MultiDocumentResponse_* with a data array + next_token; sleep model includes sleep_phase_5_min/sleep_phase_30_sec stage data, deep/light/rem/awake durations, efficiency, latency, average_breath, average_heart_rate, lowest_heart_rate, readiness embedded per sleep period; multiple sleep periods per day are possible (Sleep Routes description).
-- UNCERTAINTIES --
 ? Numeric rate-limit values are no longer published: the current spec documents only the two-layer scheme and 429 headers. The historical figure of 5000 requests per 5 minutes appeared in a search snippet attributed to a developer.ouraring.com error-handling page that now returns 404, so it could not be verified as current.
 ? Scope-name discrepancy: the OpenAPI securitySchemes list the SpO2 scope as 'spo2Daily' while cloud.ouraring.com/docs/authentication lists 'spo2'. Test which string the /oauth/authorize endpoint accepts before hardcoding; safest to try 'spo2Daily' first since it comes from the machine-readable spec. Also unclear which scopes gate the newer routes (daily_stress, daily_resilience, daily_cardiovascular_age, vO2_max) — per-route scope requirements are not annotated in the spec (all data routes just list BearerAuth/OAuth2).
 ? Webhook subscription lifetime (how far out expiration_time is set, and the required renewal cadence) is not stated in the spec — only that subscriptions have an expiration_time and a renew endpoint exists.
 ? The 'meal' webhook data_type appears in ExtApiV2DataType but has no corresponding REST usercollection route in openapi-1.37.json.
 ? developer.ouraring.com hosts a newer portal but its /docs pages returned 404 during this research (client-rendered Next.js app); cloud.ouraring.com/v2/docs remains the working canonical documentation.
 ? Access token lifetime for the authorization-code flow is not explicitly stated (only expires_in in the token response and the 30-day figure for implicit-flow tokens).
 ? Whether the deprecated /v2/usercollection/tag route has a shutdown date is not stated; it is marked deprecated in prose but not flagged deprecated:true in the OpenAPI operations.
-- IMPLEMENTATION NOTES --
Build against Oura API V2 only. Base URL https://api.ouraring.com; docs/spec at https://api.ouraring.com/v2/static/json/openapi-1.37.json (pin a copy — it is versioned and complete enough to codegen typed models from). CRITICAL: refresh tokens are single-use — persist the new refresh_token atomically on every refresh or the connection bricks. PATs are gone (deprecated Dec 2025), so even for a single-user platform you must run the full OAuth flow once and store tokens; unapproved apps allow 10 users, which is fine for Ben Health OS. Connector plan: (1) on connect, backfill each collection with start_date/end_date + next_token pagination (heartrate uses start_datetime/end_datetime); (2) create webhook subscriptions — POST /v2/webhook/subscription with x-client-id/x-client-secret headers, one per (data_type, event_type); subscribe at least to create+update for: daily_sleep, daily_readiness, daily_activity, sleep, daily_spo2, daily_stress, daily_resilience, workout, session, enhanced_tag (heartrate has NO webhook type — poll it opportunistically after a sleep webhook, or use the sleep document's embedded hr/hrv series); (3) webhook endpoint must handle GET verification (echo {\"challenge\": ...} after checking verification_token) and POST events (verify HMAC-SHA256 uppercase-hex of x-oura-timestamp + raw JSON body with client secret against x-oura-signature; ack 2xx <10s; enqueue; then GET /v2/usercollection/{data_type}/{object_id}); (4) schedule renewal via PUT /v2/webhook/subscription/renew/{id} well before expiration_time and run a nightly reconciliation poll (last ~7 days per collection) to cover missed webhooks. Model mapping: HRV and sleep stages come from /sleep (average_hrv, hrv[], sleep_phase_5_min); temperature deviation from /daily_readiness (temperature_deviation, temperature_trend_deviation); SpO2 + breathing_disturbance_index from /daily_spo2 (Gen 3+ only); stress minutes from /daily_stress; resilience level from /daily_resilience; use enhanced_tag, not the deprecated tag route. Handle 429 via Retry-After header (do not hardcode limits) and 403 as 'subscription expired or missing consent'. Use /v2/sandbox/usercollection/* for integration tests without touching real data. Expect data latency tied to ring-to-app sync: sleep/readiness only land after the Oura app opens and syncs, so design ingestion as event-driven, not fixed-schedule.

-- VERIFIED FACTS --
 . HKAnchoredObjectQueryDescriptor is `struct HKAnchoredObjectQueryDescriptor<Sample> where Sample: HKSample`, available iOS 15.4+; `result(for:) async throws` runs a one-shot snapshot query and `results(for:)` returns a long-running AsyncSequence of changes; the anchor conforms to NSSecureCoding and can be persisted across launches for incremental sync (https://developer.apple.com/documentation/healthkit/hkanchoredobjectquerydescriptor).
 . enableBackgroundDelivery(for:frequency:withCompletion:) requires the com.apple.developer.healthkit.background-delivery entitlement on iOS 15+/watchOS 8+ or it fails with errorAuthorizationDenied; HKCorrelationType is NOT supported for background delivery; on iOS, stepCount is capped at hourly regardless of requested frequency; if the app fails to call the observer update's completion handler 3 times, HealthKit stops sending updates; background delivery does not work in the Simulator (https://developer.apple.com/documentation/healthkit/hkhealthstore/enablebackgrounddelivery(for:frequency:withcompletion:)).
 . HKObserverQuery's update handler receives only the query, the set of changed sample types, a required completion handler, and an optional error — never the changed samples themselves; a follow-up query (in practice an anchored query) must fetch the actual changes; it also has a modern init(queryDescriptors:updateHandler:) form (https://developer.apple.com/documentation/healthkit/hkobserverquery).
 . HKCorrelationTypeIdentifier.bloodPressure (iOS 8.0+) combines HKQuantityTypeIdentifier.bloodPressureSystolic and .bloodPressureDiastolic into a single reading; blood pressure correlations always contain exactly two quantity samples (https://developer.apple.com/documentation/healthkit/hkcorrelationtypeidentifier/bloodpressure and .../hkcorrelation).
 . HKCorrelation has convenience init(type:start:end:objects:device:metadata:) so a device and metadata dictionary can be attached at creation; correlations are immutable and must not be subclassed (https://developer.apple.com/documentation/healthkit/hkcorrelation).
 . HKMetadataKeySyncIdentifier (iOS 11+) takes a string and MUST be paired with HKMetadataKeySyncVersion; on save, an existing object with the same sync identifier is replaced iff the new object's sync version is greater, and replacement propagates into any workout or correlation containing the old object — this is the official dedup/upsert mechanism for app-written samples (https://developer.apple.com/documentation/healthkit/hkmetadatakeysyncidentifier).
 . HKQuantityTypeIdentifier.bloodGlucose (iOS 8.0+) is a discrete mass/volume quantity read in mg/dL or mmol/L; use HKHealthStore.preferredUnits(for:) for the user's display unit; HKMetadataKeyBloodGlucoseMealTime records timing relative to a meal; Apple instructs meter apps not to save control-solution readings (https://developer.apple.com/documentation/healthkit/hkquantitytypeidentifier/bloodglucose).
 . Dexcom officially documents that the G7 app (and G7 15 Day) writes glucose to Apple Health only after a three-hour delay, not in real time, enabled via Connections tab > Apple Health > Activate (https://www.dexcom.com/en-us/faqs/how-do-i-share-my-glucose-data-with-the-apple-health-app); the same 3-hour delay is stated for Dexcom CGM apps generally, for both Apple Health and Google Health Connect (https://www.dexcom.com/en-us/faqs/integrations-and-partners/digital-health-apps).

-- IMPLEMENTATION NOTES --
Target the iOS 26 SDK with Xcode 26.x; a sensible minimum deployment target is iOS 17 or 18 — every API this connector needs (HKAnchoredObjectQueryDescriptor iOS 15.4+, background-delivery entitlement iOS 15+, clinical records iOS 12+) clears that bar easily; only earliestAuthorizedSampleDate would force iOS 27. Sync architecture: persist one HKQueryAnchor per type; on launch run HKAnchoredObjectQueryDescriptor(predicates:anchor:limit:).result(for:) to drain the backlog (it returns addedSamples and deletedObjects), then either hold results(for:) AsyncSequences while foregrounded or rely on HKObserverQuery + enableBackgroundDelivery for wake-ups — remember the observer handler carries no samples (run the anchored descriptor inside it) and its completion handler must be called or delivery stops after 3 misses; set observers up in didFinishLaunching; add both com.apple.developer.healthkit and com.apple.developer.healthkit.background-delivery entitlements; don't request background delivery for the bloodPressure correlation type (correlations unsupported) — observe bloodPressureSystolic/bloodPressureDiastolic quantity types instead, then query the correlation. Writing BP: create the two quantity samples, wrap in HKCorrelation(type:start:end:objects:device:metadata:), stamp every app-written sample with HKMetadataKeySyncIdentifier (stable per-reading key, e.g. 'benhealthos.bp.<uuid>') + HKMetadataKeySyncVersion (monotonic int) so re-syncs upsert instead of duplicating — replacement propagates into the correlation automatically. Glucose: read bloodGlucose expecting Dexcom G7/Stelo writes delayed ~3 hours (so schedule reconciliation, not real-time alerting, off HealthKit CGM data), honor preferredUnits(for:), and read HKMetadataKeyBloodGlucoseMealTime when present. Clinical records: read-only, request read-only authorization per HKClinicalType, parse HKFHIRResource.data as FHIR JSON branching on fhirVersion (DSTU2 vs R4), require the health-records value in com.apple.developer.healthkit.access plus usage string and privacy policy URL; US/UK/Canada institutions only — for a single-user personal app note the entitlement needs an App ID configured with the Clinical Health Records capability. Authorization: never gate features on read authorizationStatus (opaque by design — denied read looks like 'no data except what you wrote'); treat empty query results as indistinguishable from denial, and skip the iOS 27-beta limited-access API for now. Swift concurrency: with Xcode 26 defaults (Approachable Concurrency + MainActor default isolation on new projects), mark the HealthKit sync engine nonisolated/@concurrent explicitly, and note enableBackgroundDelivery's completion is @Sendable.

 .  .  . The older @supabase/auth-helpers-nextjs package is deprecated; @supabase/ssr is the replacement for all new projects (https://supabase.com/docs/guides/auth/server-side/nextjs)
 . RLS best practices: wrap auth functions as (select auth.uid()) so Postgres caches the result per-statement instead of per-row; index every column policies filter on; always specify the role with a TO clause (e.g. TO authenticated); check auth.uid() IS NOT NULL explicitly since it returns null for unauthenticated requests; never authorize on raw_user_meta_data (user-modifiable) — use raw_app_meta_data; break recursive cross-table policies with SECURITY DEFINER functions; auth.jwt() claims can be stale until token refresh (https://supabase.com/docs/guides/database/postgres/row-level-security)
 .
